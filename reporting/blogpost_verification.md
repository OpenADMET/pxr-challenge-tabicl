## 0. Follow-up: fixing what this report found, plus one it missed

**CPU reproduction of the GPU OOM claims.** To check whether CPU had memory headroom the GPU runs never got to use, we reran the two most memory-pressured tabular-foundation-model configurations on CPU: TabICL on the 386-column CheMeleon embedding + readout + descriptors featureset (`tabpfn_chemeleon_concat_features.py --regressor tabicl --device cpu`), and TabFM on the full 4,139-row training context with no `max_num_rows` cap. TabICL was killed by the Linux kernel's OOM-killer after growing to about 30 GB resident memory on a 31 GB-RAM machine (confirmed via `journalctl -k`, not just an unexplained process exit). This rules out the "GPU-only limitation, CPU might have headroom" premise this report's section 1 already argued against on code-path grounds; now there's a direct empirical result too. The TabFM full-context CPU case was still running at review time and is not yet resolved.

**The apples-to-apples problem (not in the original report).** `reporting/manifest.py`'s panel 03 (the "Evaluating tabular foundation models" regressor comparison) fixed the featureset at panel 02's own winning combination (CheMeleon embedding + readout + descriptors, 386 columns) and swapped only the regressor, with one silent exception: TabICL OOMs at that width, so its row alone was read from a narrower featureset (embedding + readout, no descriptors, 258 columns) instead. TabICL's row was then reported as the panel's winner and, from there, as "our best overall" for the whole post, despite never having been run on the same inputs as the five regressors it was being compared against.

We confirmed (via the CPU test above) that this isn't a fixable GPU quirk: TabICL cannot fit the 386-column featureset on this machine at all, CPU or GPU. So rather than special-case TabICL's row, we ran every regressor in that panel on TabICL's featureset (the one it can actually fit), and confirmed the 5-seed data already existed on disk for all six regressors under that narrower featureset (no new experiments were needed, just correct wiring). The ranking is unchanged: TabICL is still the panel's best regressor (0.4356 MAE) under a genuinely fair comparison, not just the best one within a definition that happened to favor it. The other five regressors' MAEs shift slightly on the narrower featureset (TabPFN v2.5 0.4437→0.4444, TabPFN v3 0.4436→0.4453, TabPFN v2.6 0.4571→0.4593, TabFM 0.4795→0.4804, LightGBM 0.4987→0.4977, XGBoost 0.5311→0.5198), all within or close to seed-to-seed noise except XGBoost, which improves outright on the leaner featureset. `reporting/manifest.py`, `reporting/blogpost.html`, `reporting/figures/figure-03.html`, and the "Evaluating tabular foundation models" section of `blogpost.md` were all updated to reflect this.

No edits had been made to `blogpost.md` as of the original report below. This report lists what checked out, what did not, and what could not be checked from this directory alone. Line references are to `reporting/blogpost.md` as it stood at that review time.

## 1. The CPU/GPU question (primary ask)

The premise to check: were the tabular-foundation-model experiments (TabPFN, TabICL, TabFM) run on CPU, with GPU used only for one-off interventions, in a way that would soften the blog's OOM (out-of-memory) claims?

**The evidence in this directory contradicts that premise.** Three independent checks:

- `_build_regressor` in `tabpfn_concat_features.py` (lines 190-245) constructs `TabPFNRegressor` and `TabICLRegressor` with no `device` argument at all, so both take the library default, which selects GPU automatically when one is visible. Only the TabFM branch sets a device explicitly, and it too picks `"cuda" if torch.cuda.is_available() else "cpu"` (line 234), i.e. it also prefers GPU.
- `logs/recipe8.log` through `recipe11.log` (the only run logs kept in this directory) show every TabPFN/TabICL/TabPFN-v2.6 invocation loading ROCm/HIP and hitting GPU-specific warnings ("Attempting to use hipBLASLt on an unsupported architecture", "Flash attention support on Navi31 GPU is still experimental"). Navi31 is an AMD GPU; this is a live GPU process, not CPU.
- No script in the repo (`tabpfn_*.py`, `run_seed_sweep*.sh`, `run_tabfm_param_sweep.py`) contains a `CUDA_VISIBLE_DEVICES`, `HIP_VISIBLE_DEVICES`, `--device cpu`, or any try/except-triggered CPU fallback. There is no code path that would selectively retry a failed fit on CPU.

So, as far as this directory's code and logs show, the tabular-foundation-model runs never touched CPU, and the OOMs are exactly what the blog says they are: GPU OOMs, with no CPU headroom ever exercised as a workaround. If anything, this makes the existing "Why is the descriptor block PCA-compressed?" section (lines 59-66) and the "PCA compression is a memory workaround" limitation (lines 95-97) *more* accurate as written, not less: both already scope the OOM to "this GPU"/"the GPU we used" and list more GPU memory, chunked attention, or a different regressor as unproven future mitigations, rather than claiming CPU was tried. I found no basis in this directory for adding a "we could selectively intervene on CPU" caveat. If you have evidence of this from the other machine (the one without these local-only results), that would need to be supplied separately. It isn't here.

## 3. Discrepancies found

**Figure 05 potent-subset R², stated range is a loose fit.** Recomputing directly from `eval_out.csv`: uncalibrated potent-subset mean R² = −8.70 (per-seed range −8.04 to −9.27), calibrated mean R² = −9.41 (per-seed range −8.64 to −9.81). The blog states "R² around −9 to −9.4" for both conditions combined (line 75). That band describes the calibrated mean well but sits outside the uncalibrated mean (−8.70). Not wrong in spirit (both are badly negative and the seed ranges do overlap that band), but worth tightening if you want the number to hold exactly rather than "around."

**Figure 06's Spearman correlation does not match this directory's own prior note.** The blog states Spearman ρ(|residual|, predicted std) = 0.2472 (n = 513) (lines 81, 85). `NEXT_STEPS.md`, this repo's own working log from the session that ran the fixed-embedding-cache rerun (and that log explicitly lists `tabpfn_uncertainty_analysis.py` as already reading the fixed cache), states **0.226** (p = 2.3e-7, n = 513) for the same statistic. The reliability-gap description also differs: the blog says the coverage gap is worst at "around −0.10 to −0.11 at the 0.4-0.6 levels" (line 85), while `NEXT_STEPS.md` says "around −0.13 to −0.14 at the 0.5-0.6 levels" with "−0.03 at 0.1, −0.05 at 0.9." I could not adjudicate which is current: `results/tabpfn_uncertainty_mordred_pca128/` (the directory the script and `NEXT_STEPS.md` both point to for `pxr_tabpfn_distributions_scored.csv` and `quantile_coverage.csv`) does not exist anywhere in this directory tree, and `figure-06.html` is a rendered SVG scatter/reliability plot with no embedded numeric text to cross-check against. **This needs `tabpfn_uncertainty_analysis.py` rerun (or the missing output files located) before the number in the blog can be confirmed.** Flagging as unresolved rather than guessing which of 0.2472/0.226 is right.

**Figure 00's dose-response-only pair reads as if it follows the same (frozen, fine-tuned) order as the sentence before it, but the underlying rows are in the opposite order.** Line 25: "frozen and fine-tuned on primary-screen + dose-response data (0.5464, 0.5573 MAE), and on dose-response-only data (0.5339, 0.5849 MAE)." The first pair is genuinely (frozen 0.5464, fine-tuned 0.5573). For the DRC-only pair, per `manifest.py`, `fine_tuned_log2fc_drc_only` = 0.5339 and `frozen_log2fc_drc_only` = 0.5849, i.e. fine-tuned is listed *first* there, reversed from the parallel structure the sentence sets up. Both numbers are correct and present, but a reader applying the same (frozen, fine-tuned) order established a clause earlier would mislabel which is which. Worth an explicit "(fine-tuned, frozen)" or reordering to keep the pattern consistent.
